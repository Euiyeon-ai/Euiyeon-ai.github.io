## Q1. 100만 명 데이터, 리스트+반복문 → 몇 분

> 동료가 만든 코드가 파이썬 리스트와 반복문으로 100만 명의 고객 데이터를 처리하는데, 실행하는 데 몇 분씩 걸려요. 이 코드를 어떻게 바꾸면 좋을지 진단하고, 구체적인 개선 방법을 제안해 주세요.

### 진단

먼저 `cProfile`로 어디에서 시간이 오래 걸리는지 확인한다. 반복문 자체가 아니라, 반복문 안에서 파일을 읽거나 DB를 조회하는 작업이 원인일 수도 있기 때문이다.

반복문이 원인이라면 이유는 두 가지다.

**① 리스트는 값을 직접 담지 않는다.** '값이 있는 주소'만 담고 있어서, 값 하나 꺼낼 때마다 주소를 따라가 찾고 → 타입을 확인하고 → 계산하고 → 결과를 새로 포장한다. 이 잔손이 100만 번 쌓인다.

**② `for`가 한 바퀴 돌 때마다 파이썬이 명령을 해석한다.** 안에서 하는 일이 아무리 단순해도 이 비용은 100만 번 그대로 붙는다.

### 개선 — `for`와 `if`를 없앤다

NumPy는 위 두 가지를 각각 없앤다. 값을 주소가 아니라 **나란히 실제로 저장**하고(연속 메모리), 안에 든 값이 **전부 같은 종류**라 하나씩 타입을 확인하지 않으며(동질 배열), 반복을 **파이썬이 아니라 C가 대신** 돈다.

| 지금 | 바꾸면 |
|---|---|
| `for` 돌며 하나씩 계산 | `arr * 1.1` — 배열 통째로 |
| `if`로 하나씩 거르기 | `arr[arr >= 100000]` — 조건 한 번에 |
| 딕셔너리에 고객별로 더하기 | `df.groupby('id')['amount'].sum()` |

```python
# 기존
result = []
for sale in sales:
    if sale >= 100000:
        result.append(sale * 1.1)

# NumPy
result = sales[sales >= 100000] * 1.1
```

숫자만 있으면 NumPy, 열 이름이 있는 표면 pandas를 쓴다.

다만 pandas로 바꿔도 `iterrows()`나 `apply(axis=1)`을 쓰면 결국 파이썬이 한 행씩 도는 것이라 안 빨라진다. 겉모양만 바뀐 경우가 많다.

그래도 느리면 숫자 타입 크기를 줄이거나, 원본이 DB에 있으면 전부 가져와서 파이썬으로 세지 말고 SQL로 집계해서 결과만 가져온다.

마지막으로 **기존 결과와 같은지 확인하고, 실행 시간을 다시 측정해 실제 개선 정도를 비교**한다. 빨라졌는데 답이 달라지면 고친 게 아니라 망친 것이다.

## Q2. 오른쪽으로 치우친 분포에 "평균 5만원"

> 고객 구매 금액 데이터가 오른쪽으로 심하게 치우친 분포를 보여요. 팀장님이 '평균 구매 금액이 5만원이니 다들 5만원 정도 쓴다고 보면 되겠네요'라고 말해요. 이 말에 어떻게 답할 건가요?

"평균 5만원"은 맞다. 틀린 건 **"다들"**이다.

고객 10명의 구매 금액이 이렇다고 해보자.

```
1, 1, 2, 2, 2, 3, 3, 5, 8, 23만원

평균 5.0만원 / 중앙값 2.5만원
```

그래프로 그리면 치우침이 바로 보인다.

```
  구매금액          인원
  ─────────────────────────────────────────────────────
   0 ~  4만원   ███████   7명   ◀ 중앙값 2.5만원. 사람은 여기 몰림
   5 ~  9만원   ██        2명   ◀ 평균 5.0만원. 정작 이 근처엔 1명뿐
  10 ~ 14만원             0명
  15 ~ 19만원             0명
  20 ~ 24만원   █         1명   ◀ 이 한 명이 전체 매출의 46%
  ─────────────────────────────────────────────────────
                          10명 / 합계 50만원
```

봉우리는 왼쪽에 있는데 꼬리만 오른쪽으로 길게 뻗어 있다. 이게 "오른쪽으로 치우쳤다"는 뜻이다. 평균보다 많이 쓴 고객은 **10명 중 2명뿐**이다. 꼬리가 평균을 그쪽으로 끌어올리기 때문이다. 반면 중앙값은 줄 세웠을 때 가운데라서 큰 값에 흔들리지 않는다.

### "치우쳤다"는 게 무슨 모양인가

고객 수가 많아지면 분포는 매끄러운 선으로 나타난다. 먼저 **치우치지 않은(좌우 대칭) 분포**다.

```
  고객 수
   ▲
   │      ●●●
   │    ●●   ●●
   │  ●●       ●●
   │●●           ●●
   └───────┴───────────▶ 구매금액
           ▲
     최빈값 = 중앙값 = 평균  (세 값이 한 점에 겹침)
```

봉우리가 가운데 있고 좌우가 같다. 이럴 때는 평균으로 "다들 이 정도 쓴다"고 말해도 된다.

반면 **오른쪽으로 치우친 분포**는 이렇다.

```
  고객 수
   ▲
   │    ●●          ◀ 봉우리(사람이 몰린 곳)는 왼쪽
   │  ●●  ●●
   │ ●      ●●
   │●         ●●●
   │             ●●●●
   │                 ●●●●●●●●●●●●●●●●●●●●●●●●  꼬리는 오른쪽으로 길게 ▶
   └───┴──┴───┴──────────────────────────────▶ 구매금액
       ▲  ▲   ▲
       │  │   └─ 평균 5.0만   ← 꼬리에 끌려 오른쪽으로 밀림
       │  └───── 중앙값 2.5만 ← 사람 수 기준 한가운데
       └──────── 최빈값 2만   ← 가장 흔한 금액(봉우리)
```

**꼬리가 뻗은 방향**을 가리켜 "오른쪽으로 치우쳤다"고 한다. 사람이 오른쪽에 많다는 뜻이 아니라 그 반대다.

세 값이 벌어지는 이유는 계산 방식이 다르기 때문이다.

- **평균**은 금액을 전부 더해서 나눈다 → 23만원짜리 한 건이 값을 통째로 끌어올린다
- **중앙값**은 줄 세운 순서만 본다 → 맨 끝 사람이 23만원이든 230만원이든 가운데는 그대로다

그래서 **최빈값 < 중앙값 < 평균** 순서가 되고, 이 세 값이 벌어져 있다는 것 자체가 치우침의 증거다. 팀장님이 말한 "5만원"은 위 그림에서 **사람이 거의 없는 자리**다.

### "그 한 명은 이상치니까 빼면 되잖아"

미리 막아둘 반론이다. 이건 특정 한 명의 문제가 아니다.

| | 전체 10명 | 최대값 1명 제외 |
|---|---|---|
| 평균 | 5.0만 | 3.0만 |
| 중앙값 | 2.5만 | 2.0만 |
| 왜도 | 2.23 | **1.35 (여전히 치우침)** |

금액이 3 → 5 → 8 → 23으로 **이어져** 있어서, 가장 큰 고객을 빼도 평균과 중앙값은 여전히 벌어진다. 한 명 지운다고 해결되는 문제가 아니라 분포 자체의 모양이다.

### 왜 중요한가

의사결정이 달라진다. 평균 5만원을 기준으로 "5만원 이상 구매 시 할인"을 만들면 해당자는 10명 중 3명이고, 나머지 7명은 이 혜택과 아무 상관이 없다. 반대로 매출의 절반 가까이를 만드는 그 한 명은 따로 관리해야 하는데 평균 안에 묻혀서 안 보인다.

그래서 세 가지를 같이 본다.

- **중앙값** — 절반의 고객이 이보다 적게 쓴다
- **가운데 절반이 쓰는 범위** — '보통 얼마 쓰는지'의 실제 폭
- **분포 그림** — 사람이 어디에 몰려 있는지

### 팀장님께 할 말

"틀리셨습니다"로 시작하지 않는다. 실제로 평균 계산은 맞기 때문이다.

> "평균이 5만원인 것은 맞습니다. 다만 고액 구매 고객 쪽으로 꼬리가 길어서 평균이 끌려 올라간 상태입니다. 실제로 평균보다 많이 쓴 고객은 10명 중 2명이고, 절반은 2.5만원 이하입니다. 중앙값과 구매금액 분포도 함께 보는 게 좋겠습니다."

말로 설득하는 대신 위 그래프에 평균선과 중앙값선을 같이 그어서 보여주면 두 선이 벌어진 게 눈으로 보인다. 그리고 지적만 하면 트집으로 들리니 **"앞으로는 중앙값과 구간별로 나눠서 보고드리겠습니다"**까지 붙인다.

## Q3. 두 팀 고객 데이터 병합

> 서로 다른 두 팀이 각자 관리하던 고객 데이터를 하나로 합쳐야 해요. 두 데이터 모두 고객 ID가 중복되거나 값이 다르게 기록된 행이 있고, 결측치도 섞여 있어요. 어떤 순서로 이 작업에 접근할 건가요?

**기준 확인 → 중복 정리 → 합치기 → 결측치 처리 → 검증** 순서로 진행한다.

```
      A팀 데이터                        B팀 데이터
   ┌──────────────┐                 ┌──────────────┐
   │  ID: C001    │                 │  ID: 001     │
   │  1,200행     │                 │  900행       │
   │  빈칸·중복 O │                 │  빈칸·중복 O │
   └──────┬───────┘                 └───────┬──────┘
          │                                 │
          └────────────────┬────────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │ ① 기준 확인                          │
        │   · ID 형식 통일  001 → C001         │
        │   · 컬럼 의미 대조 ('구매액' = 누적?) │
        │   · 각 데이터 상태 따로 기록          │
        └──────────────────┬───────────────────┘
                           │
          ┌────────────────┴────────────────┐
          ▼                                 ▼
   ┌──────────────┐                 ┌──────────────┐
   │ ② 중복 정리  │                 │ ② 중복 정리  │   ◀ 합치기 前
   │ 1,200 → 1,050│                 │  900 → 880   │     (행 폭발 방지)
   └──────┬───────┘                 └───────┬──────┘
          │                                 │
          └────────────────┬────────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │ ③ 합치기  outer join                 │
        │   → 1,180행                          │
        │   행 수 예상보다 많으면 ②로 되돌아감 │
        └──────────────────┬───────────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │ ④ 결측치 처리                        │   ◀ 합친 後
        │   1) 상대 팀 값으로 먼저 메움         │     (진짜 값 살리기)
        │   2) 그래도 남은 빈칸만 이유별 처리   │
        └──────────────────┬───────────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │ ⑤ 검증                               │
        │   고객 수 · 중복 ID · 결측 수 ·       │
        │   매출 합계  =  원본과 대조           │
        └──────────────────┬───────────────────┘
                           ▼
                   최종 통합 테이블
```

### 단계별 근거

| 단계 | 하는 일 | 왜 이 자리인가 |
|---|---|---|
| 1. 기준 확인 | `C001` vs `001` 형식 통일, 컬럼 의미 대조 | 여기가 어긋나면 합쳐도 매칭 0건 |
| **2. 중복 정리** | 완전 동일 행 제거, 값 다르면 '최신 우선' 등 기준 정하기 | **합치기 전**이어야 행이 안 불어남 |
| 3. 합치기 | 목적에 맞는 join (전체 명단이면 `outer`) | 2번에서 정한 기준대로 충돌 값 선택 |
| **4. 결측치 처리** | 상대 팀 값으로 채우고, 남은 것만 따로 | **합친 뒤**여야 진짜 값이 들어옴 |
| 5. 검증 | 고객 수·중복 ID·결측 수·매출 합계를 원본과 대조 | 늘어나거나 사라진 것 잡아냄 |

### 왜 중복이 먼저인가 — 행 폭발

```
  [정리 안 하고 합치면]
     A팀              B팀              결과
  ┌──────────┐    ┌──────────┐
  │ C001 │5만│    │ C001 │3만│     2 × 2 = 4행
  │ C001 │5만│ ×  │ C001 │3만│     매출 8만 → 16만  (2배 뻥튀기)
  └──────────┘    └──────────┘     합친 뒤엔 어디서 불어났는지 못 찾음
      2행             2행

  [중복 먼저 정리하면]
  ┌──────────┐    ┌──────────┐
  │ C001 │5만│ ×  │ C001 │3만│     1행, 합계 그대로
  └──────────┘    └──────────┘
```

### 왜 결측치가 나중인가 — 진짜 값 덮어쓰기

```
  [먼저 채우면]                       [합친 뒤 채우면]

  A팀: C001 │ (빈칸)                  A팀: C001 │ (빈칸)
        ↓ '미상'으로 채움                   ↓ 먼저 합침
  A팀: C001 │ 미상                    합침: C001 │ (빈칸) ← B팀에 값 있음
        ↓ B팀과 합침                        ↓ B팀 값으로 채움
  결과: C001 │ 미상                   결과: C001 │ 010-1234-5678
        진짜 값이 못 들어옴                  남은 빈칸만 따로 처리
```

### 한 줄 요약

**중복은 합치면 커지니까 먼저, 결측치는 합치면 줄어드니까 나중.**
