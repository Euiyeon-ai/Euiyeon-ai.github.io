## Q1. Train 99%, Test 70% — 무엇을 의심할 건가요?

> 학습 데이터에서는 정확도 99퍼센트가 나오는데, 테스트 데이터에서는 70퍼센트밖에 나오지 않는 모델을 넘겨받았어요. 어떤 원인을 의심하고, 어떤 방법으로 개선을 시도할 건가요?

**질문의도**: train-test 성능 차이가 왜 생겼는지 체계적으로 진단할 수 있는가 — 증상만 보고 원인을 짐작하지 않고, 가설을 세우고 확인한 뒤 개선하는 순서를 밟을 수 있는가.

### "과적합이다"로 바로 넘어가지 않는다

train 점수와 test 점수가 크게 벌어지면 다들 반사적으로 "과적합이네"라고 생각한다. 그런데 사실 이 증상 하나에는 원인이 될 만한 후보가 두 가지 숨어 있고, 둘은 겉으로 보이는 모습이 똑같다.

1. **모델이 train 데이터를 통째로 외워버렸다** (진짜 과적합)
2. **train과 test가 애초에 서로 다른 종류의 데이터다** (분포 차이)

두 경우는 원인도, 고치는 방법도 완전히 다르다. 그래서 손부터 대기 전에 둘 중 어느 쪽인지부터 가려야 하는데, 이때 쓰는 게 **k-fold 교차검증(CV)**이다.

### 교차검증으로 갈림길을 가른다

CV는 test 데이터는 아예 쳐다보지도 않고, train 데이터만 여러 조각으로 잘라서 서로 돌아가며 검증용으로 써보는 방법이다. 말하자면 "이 모델한테 진짜 처음 보는 데이터를 줘도 여전히 잘할까?"를 test를 열어보기 전에 미리 연습해보는 셈이다.

![train-test 성능차 진단 흐름. train 99%, test 70%라는 증상에서 시작해 k-fold 교차검증을 해본다. CV 점수도 낮게 나오면 진짜 과적합이므로 모델 복잡도를 낮추거나 데이터 누수를 확인하고, CV 점수는 높은데 test에서만 낮다면 train과 test의 분포·수집 시점·대상 차이를 확인한다](/images/weekly-paper-4/q1-diagnosis-flow.svg)

이 결과에 따라 다음에 할 일이 완전히 갈린다.

| CV 결과            | 의미                                    | 확인·개선 방법                                                                                                                                         |
| ---------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **CV도 ~70%로 낮다** | train 안에서조차 처음 보는 데이터엔 약하다 → 진짜 과적합   | ① 모델이 너무 복잡한 건 아닌지 확인 (결정트리라면 깊이가 지나치게 깊지 않은지) → `max_depth`, `min_samples_leaf` 등으로 단순화<br>② 데이터 누수 확인 — 사실상 정답을 미리 알려주는 컬럼이 feature에 섞여 있진 않은지 |
| **CV는 ~99%로 높다** | train 안에서는 멀쩡하게 일반화됨 → 유독 test에서만 무너짐 | train과 test 사이 변수 분포, 클래스 비율, 수집 시점·대상 차이 확인 → 데이터 불균형 의심                                                                                        |

### 왜 이 순서가 중요한가

CV를 건너뛰고 곧장 "모델이 복잡해서 그렇다"고 단정해버리면, 실제 원인이 데이터 불균형일 경우 모델을 아무리 단순화해도 test 점수는 변하지 않는다. 반대로 CV에서 이미 70%로 떨어진다면, train과 test 데이터가 얼마나 다른지 찾아보는 의미가 없어진다 — 문제는 애초에 모델이 train을 통째로 외운 것이니까.

정리하면, **같은 증상(train↔test 점수차)이라도 원인은 두 갈래로 갈릴 수 있으니, 뭔가 고치기 전에 CV로 먼저 확인해야 한다.

## Q2. 대출 거절 사유를 설명해야 한다면 — 단일 결정 트리 vs 앙상블

> 은행에서 대출 승인 여부를 예측하는 모델을 만들고 있어요. 법적으로 왜 거절되었는지를 고객에게 설명할 수 있어야 해요. 단일 결정 트리와 랜덤 포레스트나 그레이디언트 부스팅 중 어떤 모델을 선택할 건가요?

**질문의도**: 성능과 설명 가능성 사이의 trade-off를 이해하는가 — 정확도가 가장 높은 모델이 항상 정답은 아니고, 상황(여기서는 법적 요구사항)에 따라 어떤 모델을 고를지가 달라진다는 걸 아는가.

### 결론: 단일 결정 트리를 기준 모델로 선택

단일 결정 트리를 고르는 이유는 간단하다. 어떤 고객이 왜 거절됐는지, 조건을 하나씩 따라가기만 하면 그대로 설명이 되기 때문이다. 예를 들면 "부채비율이 40%를 넘고 소득이 300 미만이라 거절"처럼, 조건 → 조건 → 결과로 이어지는 하나의 길이 눈에 보인다.

반면 랜덤 포레스트는 수십에서 수백 개나 되는 트리가 각자 판단을 내리고, 그 결과를 투표로 합친다. 그레이디언트 부스팅도 여러 모델의 예측을 차례로 쌓아 올리는 방식이라 사정은 비슷하다. 둘 다 "왜 거절됐나요?"라는 질문에 하나의 이유로 답하지 못한다.

![단일 결정 트리와 앙상블의 설명 가능성 차이. 단일 결정 트리는 부채비율이 높고 소득이 낮다는 조건을 따라가면 거절이라는 하나의 경로로 설명할 수 있지만, 랜덤 포레스트나 그레이디언트 부스팅은 여러 개의 작은 트리가 각자 판단한 결과를 투표하거나 누적해서 최종 결과를 만들기 때문에 한 고객이 왜 거절되었는지를 하나의 경로로 보여주기 어렵다](/images/weekly-paper-4/q2-tree-vs-ensemble.svg)

|                | 단일 결정 트리                                          | 랜덤 포레스트 · 그레이디언트 부스팅                          |
| -------------- | ------------------------------------------------- | --------------------------------------------- |
| **거절 사유 설명**   | 조건 경로 하나로 명확하게 제시 가능                              | 여러 트리의 투표·누적 결과라 경로 하나로 못 보여줌                 |
| **예측 성능**      | 상대적으로 낮음                                          | 상대적으로 높음                                      |
| **법적 요구사항 대응** | "부채비율 40% 초과 + 소득 300 미만"처럼 규제기관이 요구하는 수준의 설명에 적합 | 사후 설명 기법(SHAP 등)을 붙여도 단일 트리와 동일한 설명력을 보장하지 않음 |

### 다만 성능을 무조건 포기하지는 않는다

그렇다고 설명 가능성 하나 때문에 성능을 마냥 포기할 수는 없다. 실제 업무라면 이런 순서로 접근하겠다.

1. **단일 결정 트리를 기준(baseline) 모델**로 먼저 만든다.
2. 랜덤 포레스트·그레이디언트 부스팅도 같이 돌려서 성능을 비교해본다.
3. 복잡한 모델 쪽 성능이 훨씬 좋다면, 그때 SHAP 같은 사후 설명 기법을 검토한다. 다만 사후 설명을 붙인다고 단일 결정 트리만큼 설명이 명쾌해지는 건 아니라는 점은 염두해둔다.
4. 무엇보다 **법적·규제적으로 어느 수준의 설명까지 요구되는지를 먼저 확인**하고, 그 기준에 맞춰 최종 모델을 정한다.

### SHAP이란 — 이미 나온 결과 하나를 뜯어서 "왜?"를 계산해보는 도구

SHAP은 모델을 다시 만들거나 단순하게 바꾸는 방법이 아니다. 모델은 그대로 두고, **이미 나온 예측 결과 하나만 붙잡아서 "여기에 각 feature가 얼마씩 영향을 줬을까"를 나중에 거꾸로 계산해주는 도구**다. 그래서 예측이 끝난 뒤에 설명을 덧붙인다는 뜻으로 "사후(post-hoc) 설명"이라고 부르고, 랜덤 포레스트든 그레이디언트 부스팅이든 모델을 가리지 않고 아무 데나 붙일 수 있다.

계산 방식은. "이 feature가 있을 때와 없을 때, 예측이 얼마나 달라지는가"를 모든 feature에 대해 하나씩 확인해보고, 그 차이만큼을 그 feature의 몫으로 인정해주는 것이다. (내부적으로는 게임이론의 섀플리 값이라는 계산법을 쓰는데, "여럿이 만든 성과를 각자 기여만큼 공평하게 나눠 갖는 방법"이다.)

예를 들어 어떤 고객의 거절 확률이 71%로 예측됐다면, SHAP은 그 71%가 어디서 왔는지를 이렇게 쪼개서 보여준다.

![SHAP 기여도를 기준값부터 최종 예측까지 차례로 더해가는 흐름. 기준값 40%에서 시작해 부채비율 높음이 25%p를 더해 65%가 되고, 소득 낮음이 18%p를 더해 83%가 되고, 신용거래 기간 김이 12%p를 빼서 최종 거절확률 71%가 된다](/images/weekly-paper-4/q2-shap-waterfall.svg)

| feature | 기여도 |
|---|---|
| 부채비율 높음 | 거절 쪽 +25%p |
| 소득 낮음 | 거절 쪽 +18%p |
| 신용거래 기간 김 | 승인 쪽 −12%p |
| (기준값) | 40% |

이 표만 보면 "부채비율과 소득이 거절 쪽으로 크게 작용했구나"까지는 알 수 있다.

**다만 이게 단일 결정 트리만큼 명쾌한 설명은 아니다.** 결정 트리는 "이 조건을 만족하면 무조건 거절"이라는 규칙 자체를 보여주는데, SHAP은 그런 규칙 없이 "대략 이 정도 영향을 준 것 같다"는 추정치만 준다. 계산할 때마다 숫자가 조금씩 달라질 수도 있고, "왜 이런 규칙이 적용됐는가"가 아니라 "이 예측에 이 feature가 얼마나 거들었나" 정도로만 답해준다. 위 3번에서 "사후 설명을 붙인다고 단일 트리만큼 설명이 명쾌해지는 건 아니다"라고 한 게 이 이야기다.

결국 이 문제의 기준은 "가장 정확도가 높은 모델"이 아니라, **예측 성능·설명 가능성·규제 요구사항, 이 셋 사이의 균형**이다.
